### D-001 · 2026-11-06 · Development and verification environment

### D-002 · 2026-11-06 · Swift Package instead of an `.xcodeproj`
- **Decision:** A SwiftPM package with three modules — `FrameStackCore` (pure engine), `FrameStackMedia` (AVFoundation/Core Image/ImageIO), `FrameStack` (SwiftUI app) — plus two test targets. ### D-004 · 2026-11-06 · Working color space and Average math
- **Decision:** Each decoded frame is interpreted by **Core Image using the buffer's own color tags** (YCbCr matrix, primaries, transfer function), orientation-corrected, and rendered to **extended linear sRGB (Rec.709 primaries, D65), Float32 RGBA, premultiplied**. Average = per-channel `sum / N` with **Float64 accumulators** (vDSP), so N identical frames reproduce the frame bit-exactly and no 8-bit rounding happens between frames. Preview and export run the identical pipeline; preview only adds a Lanczos downscale in linear light before accumulation (linear ops commute with averaging).
- **Alternatives:** Averaging gamma-encoded values (what naive tools do; visibly darker trails — e.g. a 2-of-24 white trail becomes 21/255 instead of 82/255). May be offered later as an explicit creative "display-referred" option (PRD §5.1).
- **Reason:** PRD §5.1/§14 default; physically meaningful long-exposure look.
- **Notes:** For BT.709-tagged video, the linearization curve is whatever Core Image/ColorSync assigns to that tag — the same interpretation QuickTime Player uses for display. Tests are written to be independent of that choice (black/white, relative and same-pipeline comparisons). HDR (HLG/PQ) sources are flagged with a warning; highlights above SDR white are clipped at export.
- **Memory:** accumulator = `W × H × 4 × 8` bytes (4K ≈ 265 MB) + one Float32 frame (≈ 133 MB), independent of frame count.
- **Revisit when:** M4 color-management work (Display P3 export, 10-bit decode), M6 HDR handling, or the owner asks for a gamma-space look.

### D-005 · 2026-11-06 · M1 export: PNG, sRGB, 8- or 16-bit RGB
- **Decision:** Linear → clamp each channel to [0,1] → IEC 61966-2-1 sRGB transfer (Float64) → round to nearest → 8- or 16-bit RGB PNG tagged sRGB. Default **16-bit** (smooth averages band in 8-bit). No dithering, no alpha channel. A composite with any alpha < 0.999 is **rejected** rather than silently flattened. Files are written to a temp file and atomically moved into place, then **read back** to verify dimensions and bit depth.
- **Alternatives:** Embedding the linear data in a float TIFF/EXR (later, M4/M6); Display P3 output (M4).
- **Reason:** PRD §14 (native-size PNG in M1) and §7 (never claim a bit depth not verified by reading the file).
- **Revisit when:** M4 (JPEG/TIFF, wide gamut, alpha), M6 (16-bit TIFF with profiles).

### D-006 · 2026-11-06 · Frame identity, scanning and ranges (revised after first CI run)
- **Decision:** A frame **is** the presentation timestamp the **decoder** reports (`FrameTime`, exact rational, 128-bit cross-multiplied comparisons). On import, the track's compressed samples are read with `AVAssetReader` passthrough (no decode) and **mapped through the track's edit list** (`AVAssetTrack.segments`): a sample at media time *m* inside a segment's source range is presented at `m − source.start + target.start`; samples outside every segment are not presented. If any segment changes speed, an edit starts mid-frame, or the CMTime arithmetic would round, the scan **falls back to decoding every frame** and uses the decoder's timestamps. Samples flagged *DoNotDisplay* are skipped; duplicate timestamps keep the first sample. Until the scan finishes the UI shows `duration × fps` labeled "estimate". Ranges are `[start, end)`. Rendering decodes only `[first selected, last selected]`, matches decoded frames by exact timestamp, and **reports** any selected timestamp that never decodes (`missingFrames`) instead of substituting another frame.
- **Evidence:** The first CI run showed passthrough sample timestamps are in *media* time while decoded frames are in *presentation* time: on the B-frame fixture (ffmpeg writes an edit list with a 2-frame offset) timestamp *k* decoded frame *k + 2* and the last two timestamps were reported missing. The frame-index fixture and missing-frame reporting caught it. A test now requires the fast scan to equal the decode scan on every fixture, including a stream-copied trim (`trimmed_editlist.mp4`, frames 30–44 stored but outside the edit).
- **Alternatives:** Always decode during scan (exact but slow on long clips — kept as the fallback and as the test reference); `AVSampleCursor` (media timeline, same problem).
- **Reason:** PRD §4.3 — actual timestamps, edit lists and VFR handled deterministically, no fabricated counts.
- **Revisit when:** A real clip triggers the decode fallback often enough to make import slow, or reports missing frames.

### D-007 · 2026-11-06 · Exact Count distribution
- **Decision:** Over M eligible frames, position_i = round_half_up(i·(M−1)/(K−1)) for i in 0..<K (exact integer arithmetic). K = 1 picks index ⌊(M−1)/2⌋ (lower middle for even M). K > M selects all M frames and shows a notice. Distribution is **by index**, not by time (identical for constant frame rate; for VFR footage this means "every k-th frame", not "every k seconds").
- **Reason:** PRD §4.3 ("deterministic index distribution", endpoints included, never duplicate).
- **Revisit when:** Custom/time-uniform sampling patterns (P2).

### D-008 · 2026-11-06 · Preview scheduling
- **Decision:** Any settings change bumps a revision, recomputes the selection synchronously, and schedules a preview render after a 250 ms debounce, cancelling the previous one. Snapshots carry the revision they were rendered for; an older snapshot is dimmed and labeled "Preview outdated". Preview resolution: 1080 px long edge (default), 2160 px, or full. Export always renders at native resolution and cancels any in-flight preview first (one heavy render at a time).
- **Reason:** PRD §8.2, §10.1.

### D-009 · 2026-11-06 · Decode pixel format 32BGRA (8-bit per frame)
- **Decision:** Frames are decoded to 32BGRA. Each frame is quantized once by the decoder (8-bit sources lose nothing meaningful); accumulation is in Float64.
- **Alternatives:** 10-bit YCbCr or half-float RGBA output.
- **Reason:** Most robust decoder output across codecs and Macs for the first slice.
- **Limitation:** 10-bit (e.g. HEVC Main10/HDR) sources lose precision per frame. **Revisit in M4.**

### D-013 · 2026-11-06 · Damaged files: undecodable frames are missing frames, not a failed render
- **Decision:** When `AVAssetReader` fails mid-stream (status `.failed`, e.g. "Cannot Decode" on an invalid NAL unit), `CompositeRenderer` creates a new reader starting at the next *selected* frame after the last frame the decoder delivered and continues. Frames that never decode are listed in `CompositeResult.missingFrames`, the reasons in `decodeFailures`, and the UI shows "N selected frames could not be decoded: <reason> after <time>" in the bottom bar and in the export report. No frame is ever substituted for a missing one. Every restart strictly advances (so it terminates) and is capped at `maxDecoderRestarts = 256`; past the cap the summary says the renderer gave up and the file is badly damaged. If nothing at all decodes the render still throws.
- **Evidence:** The owner's `Sexy Spelling Song.m4v` (a 2010 podcast download; ffmpeg reports "Invalid NAL unit size" on most access units) imported and scanned fine (first frame decodes) but every render aborted with a bare "Cannot Decode". With this policy it yields a 73-frame composite and an honest warning; the frame count varies by one or two between runs because the hardware decoder's failure point is not deterministic on that file. A deterministic fixture, `corrupt_frame_75.mp4` (count clip with one NAL length overwritten), loses frames 73–91 on macOS 27 / M4 Pro: the two B-frames presented before the damaged P-frame reference it, and recovery needs the next keyframe plus the reorder delay. Tests assert the decoder-independent guarantee (loss confined to the damaged GOP and its neighbour; everything else decodes; frame identity preserved after the damage).
- **Alternatives:** Fail the whole render (previous behavior — useless on a long clip with one bad frame); jump to the next keyframe (faster recovery, but needs sync-sample info the scanner does not record yet — worth adding when M3 scrubbing needs keyframes anyway); software decoding fallback (AVFoundation offers no switch).
- **Limitation:** The scanner's *decode* fallback path (used only when an edit list cannot be mapped) still aborts on a damaged sample; such a file then fails at import with the reader's message.
- **Revisit when:** keyframe positions are recorded (M3), or a real file shows the one-frame-at-a-time restart being too slow.

### D-017 · 2026-11-06 · M2 blend-mode mathematics
- **Decision:** All modes operate on the same working-space frames as Average (linear light, Rec.709/sRGB primaries, premultiplied Float32 RGBA, oriented, optionally Lanczos-downscaled for preview) through a `FrameReducer` protocol (`add(frame)`, `result()`; output-sized state only). Per mode:
  - **Average** — `Σ/N`, Float64 (unchanged, D-004).
  - **Lighten / Darken** — per-channel running max / min, Float32, exact; alpha reduced the same way. Order-independent; opacity ignored.
  - **Additive** — `Σ frame × opacity`, Float64. Values above 1 are kept and clipped only by the export encoder (D-005). Alpha sums too (an opaque N-stack has alpha N·opacity; the exporter treats alpha ≥ 1 as opaque). Order-independent. Normalisation/exposure control is M6.
  - **Screen / Multiply / Difference / Normal** — sequential, oldest to newest. The **first selected frame initialises the composite unchanged** (at any opacity). Every later frame F updates each colour channel of the composite C as `C' = C + opacity × (B(C, F) − C)` with B = `C + F − C·F` (screen), `C·F` (multiply), `|C − F|` (difference), `F` (normal). Alpha always uses the normal rule, so opaque video stays opaque. Normal at opacity 1 is therefore exactly the last selected frame; at opacity a the k-th-from-last frame has weight a(1−a)^k (geometric), which is *not* an equal-weight average (PRD §5.1). Screen/Multiply are computed in **linear light**, not display-encoded values as Photoshop does, so they are brighter/darker than the Photoshop look; this is deliberate (same physical space as Average) and documented in the mode's info text. Float32 state; 1000 sequential multiplies of 0.999 match the Double reference within 2e-4.
  - **Opacity** is clamped to 0…1 and only re-renders modes where `usesOpacity` is true.
- **Order guarantee:** the renderer decodes in presentation order (AVAssetReader output, including after a decoder restart, D-013) and reports `deliveredInPresentationOrder`. Reversed/ping-pong order is M6.
- **Verification:** `BlendModeTests` (1×1 fixed references per mode, two-frame and large-count, opacity, random-data vs scalar Double reference for all 8 modes, bounded footprint); `BlendModeRenderTests` (black/white and moving-square fixtures per mode, "Normal 100 % = last *selected* frame", Lighten/Darken bit patterns on the count clip, preview = export for every mode); `AppModelTests` (mode/opacity changes re-render, Average ignores opacity, export file names).
- **Alternatives:** display-encoded (gamma) blending for Screen/Multiply (may be added as an explicit creative option, cf. D-004); Float64 state for sequential modes (unnecessary at these counts); SIMD/vDSP kernels for the sequential loop (not needed yet — see timings in the plan's log; optimise after measuring, PRD §10.2).
- **Revisit when:** Median / luminance modes (M6, need different data structures), reversed order, or a gamma-space creative mode is requested.

### D-018 · 2026-11-06 · M3 workflow semantics: timeline handles, playhead, source frames, undo, zoom
- **Range handles:** the in handle snaps to a frame's timestamp; the out handle snaps to a *boundary* — the next frame's timestamp or the clip duration — so the range always stays `[frame start, next frame start)` and the "Last frame" field is inclusive (`FrameTimeline.range(firstFrame:lastFrame:end:)`). Dragging either handle past the other keeps one frame selected rather than producing an empty range. The filmstrip outside the range is dimmed. Each drag is one undo step.
- **Playhead:** an index into the scanned timeline (not a time), so stepping is frame-exact on variable-frame-rate footage. Click/drag on the strip, ← → (⇧ ×10), Home/End when the strip has focus, ⌥← ⌥→ from the Frame menu anywhere, a frame-number field in the bottom bar. I / O (⌥I / ⌥O) set the in/out point at the playhead; setting an out point before the in point moves both to that frame.
- **Original frame view:** decoded by `AVAssetImageGenerator` with zero tolerance and the display transform applied (`SourceFrames.frame`), bounded to the preview quality's long edge. This is display-referred output from Apple's own pipeline, verified within 1/255 of FrameStack's working-space render (RealClipTests), so Original and Composite are comparable on screen. Compositing never uses it. Thumbnails use the same generator with a half-bin tolerance *before* the requested time (cheap keyframes, distinct and ascending).
- **Undo/redo:** `CompositeSettings` (range, sampling, blend, opacity) is the undoable state; every change registers one step with an action name on the window's `UndoManager`; interactive edits (handle drags, the opacity slider) are grouped; preview quality, view mode, zoom and the playhead are not undoable; opening a file clears the stack. Redo registration relies on `apply` running synchronously inside the undo closure.
- **Zoom:** percentages are relative to the source's full display resolution, so "100 %" is one source pixel per point regardless of preview quality (a 1080 px preview is upsampled at 100 %; choose Full quality for a true pixel view). Fit / 100 % / fixed steps / pinch; scroll to pan; checkerboard behind the image for future alpha sources.
- **Recent Files:** paths in `UserDefaults` (max 10, most recent first, only successful opens), plus `NSDocumentController` so the Dock menu lists them. No security-scoped bookmarks yet (no sandbox, D-002).
- **Inspector sections** are `DisclosureGroup`s with per-section persisted state.
- **Known limitations:** side-by-side views scroll independently and start at the top-left when zoomed; the opacity slider and text fields cannot be driven through the accessibility value API (D-015).

### D-019 · 2026-11-06 · `.framestack` project: one JSON file, bookmark + fingerprint, relink policy
- **Format:** a single JSON document (`formatVersion` 1, `ProjectFile` in FrameStackMedia), not a package. Human-readable and diffable, written atomically, and it works for an app built by `swift run` without a document-type registration. Contents: a source reference (alias-style bookmark, absolute path, path relative to the project file, identity = file name / size / modification date / fingerprint, duration, display size, scanned frame count), `CompositeSettings` (range, sampling, blend, opacity), `ExportSettings` (format, depth, JPEG quality, sizing, color space) and light UI state (preview quality, view mode, playhead). The selected frame timestamps are **not** stored: they are recomputed deterministically from range + sampling + the rescanned timeline (PRD §9.1 allows "a deterministic policy"); a different scan result on reopen is reported, never hidden.
- **Fingerprint:** SHA-256 over `size ‖ first MiB ‖ last MiB` (`SourceIdentity`). Hashing whole multi-gigabyte clips would make every save and open slow; the modification date alone changes on every copy. Limitation: an edit that preserves the size and both ends is not detected. A rename or copy is the same media.
- **Resolution order on open (`SourceLocator`):** bookmark → saved absolute path → path relative to the project file. The first existing candidate whose fingerprint matches is used silently (a moved or renamed file therefore just works and the project shows "Unsaved changes" so the new location can be saved). An existing file that does *not* match stops at a **"Video has changed"** screen naming the differences; no candidate at all stops at **"Video not found"**. Both offer Locate… (the chosen file is checked the same way) and Cancel; only the changed screen offers **Use This File Anyway**, which is the user's explicit decision — the notice stays in the Project section and the project is marked edited. Different media is never used silently (PRD §9.1).
- **Reopen semantics:** settings are applied after the clip is rescanned; a saved range that does not fit a shorter clip is clamped and reported; frame-count / duration / size differences are reported in `sourceNotice`. Export settings and UI state are restored.
- **Unsaved changes:** compositing or export settings differ from the saved document (for a never-saved clip: from the state right after opening). UI state never counts. ⌘Q asks Save / Don't Save / Cancel. Export settings follow the user from clip to clip, but leaving a project resets them so a project's choices do not leak into an unrelated video.
- **Type:** `local.framestack.project`, conforming to `public.json`, declared in the bundle's Info.plist (Finder opens `.framestack` with FrameStack; `swift run` builds fall back to a dynamic `UTType(exportedAs:)`). Files with a newer `formatVersion` are refused with a clear message instead of being half-read.
- **Revisit:** when masks (M6) need raster data, move to a package (`formatVersion` 2) with explicit migration; consider auto-save then.

### D-020 · 2026-11-06 · 10-bit and HDR sources decode to half-float (revisits D-009)
- **Decision:** `CompositeRenderer.makeOutput` asks the reader for `kCVPixelFormatType_64RGBAHalf` when the format description reports `BitsPerComponent` > 8 or the track is HDR, and for 32BGRA otherwise; if the reader refuses half-float it falls back to 32BGRA. `VideoSourceInfo.bitsPerComponent` is shown in the inspector ("hvc1 · 10-bit").
- **Evidence:** the `tenbit_ramp_10f.mp4` fixture (HEVC Main10, lossless, a 876-code luma ramp over 320 columns) renders with 320 distinct values through the half-float path and 205 through 8-bit on the owner's Mac; a 16-bit PNG export keeps them. 8-bit H.264 clips carry no `BitsPerComponent` extension and keep the 8-bit path (no behavior change for existing footage).
- **HDR policy (unverified on real footage — no HDR clip was available):** no tone mapping. Core Image converts PQ/HLG-tagged frames to the linear working space relative to SDR white; values above 1.0 survive accumulation and are clipped on export; the Source section warns. Revisit with an iPhone HDR clip: decide between clip, a documented tone curve, or an HDR output format.

### D-021 · 2026-11-06 · Export formats, output sizing and output color space
- **Formats:** PNG (8/16-bit), JPEG (8-bit, quality 0.5…1, default 0.92), TIFF (8/16-bit, LZW). All written by ImageIO to a temp file, moved into place, then **read back** to verify dimensions, bit depth, container type and ICC profile; any mismatch is an error, never a silent misreport (PRD §7 "do not claim otherwise until tested by reading exported file metadata"). A 16-bit request with JPEG is downgraded and reported as 8-bit.
- **Sizing:** native, long-edge cap, or percent — downscale only (FrameStack never invents pixels). The resample is the same Lanczos-in-linear-light step the preview uses, applied per frame before accumulation, so a 50 % export is mathematically the same as a 50 % preview.
- **Color space:** sRGB (default) or Display P3. P3 output applies a 3×3 linear matrix derived at run time from the CIE chromaticities (both spaces are D65, no adaptation), then the same transfer curve, clamp and rounding, and tags the file with the Display P3 profile. Verified: the P3 PNG color-managed back to sRGB by CoreGraphics matches the sRGB export within 1/255, and sRGB red lands at the reference P3 coordinates (0.8225, 0.0332, 0.0171). No "embed the source profile" option: video sources carry tags, not ICC profiles. Rec. 2020 / HDR outputs are out of scope until D-020's HDR policy is settled.
- Export settings live in the project (D-019) and are not undoable.

### D-022 · 2026-11-06 · Image sequences: one `MediaSource`, sequence time, canvas and alpha policy
- **Model:** `MediaSource` is either a `VideoSourceInfo` or an `ImageSequenceInfo` (a folder, or a chosen set of stills). The sampler, reducers, preview/export, timeline UI, undo and project document are unchanged: the renderer gained a second frame producer (`decodeSequence`) that feeds the same per-frame step as the video decoder (orient → size check → Lanczos in linear light → reduce). PRD §10.3 `SourceDocument`/`SourceImporter` are `MediaSource` + `ImageSequenceLoader`.
- **Which files:** a folder → every readable JPEG/PNG/TIFF/HEIF in it (non-images and undecodable headers are listed as skipped, with a warning, never silently); one image → its whole folder; several chosen files → exactly those. Natural (Finder) name order (`localizedStandardCompare`), so `frame_10` follows `frame_9`. Reverse order is an explicit toggle. RAW is not attempted (PRD §4.2 "later exploration").
- **Time axis:** still *i* sits at `i ÷ rate` **sequence seconds** (`FrameTime(value: i·1000, timescale: rate·1000)`, exact for 29.97/23.976), duration is one interval past the last still, the UI says "sequence time" in the Source and Time Range sections and never shows these as recorded timestamps (PRD §4.2). Changing the rate or the order keeps the selected *images* (first/last indices are carried over, mirrored for reverse). Default 30 fps.
- **Canvas policy:** every still must have the same oriented size as the first; otherwise import fails naming the canvas file and the offenders ("FrameStack does not stretch or pad images silently"). Fit/Fill onto a common canvas is M5c work (crop/canvas) and will be an explicit choice. Real-world note: a phone burst mixing landscape and portrait shots fails this check by design.
- **Orientation and colour:** EXIF orientation from the header is applied by Core Image (`oriented`), so a "Rotate 90 CW" JPEG composites upright and the canvas is its oriented size; thumbnails and the Original view use ImageIO's transform-applying thumbnail path. Embedded profiles (e.g. Display P3 phone JPEGs) are honoured by Core Image into the linear working space; a P3 red lands at (1.22, −0.04, −0.02) linear sRGB, exports back to (255, 0, 0) in P3 and clips per channel in sRGB (no gamut mapping — same as video, D-005).
- **Alpha:** PNG/TIFF stills may be transparent. Frames are premultiplied RGBA in the working space, so a transparent pixel contributes no light and the accumulated alpha records coverage (an Average over partly transparent frames is the average of the frames that cover each pixel, with the coverage in alpha). Exports keep a straight alpha channel in PNG/TIFF (`CGImageAlphaInfo.last`, alpha linear, colour un-premultiplied); JPEG cannot, so it is composited over black and the report says so (`ExportReport.alphaFlattened`). The preview is drawn over the checkerboard. `MediaError.transparencyNotSupported` is gone.
- **Project document → format 2:** `source.kind` (`video` / `imageSequence`) and `source.sequence` (file names in natural order, rate, reversed); format-1 files read unchanged (kind defaults to video). A sequence's identity is `SHA-256` over `name ‖ size` of every still (never the pixels — a sequence may be thousands of files) plus the total size; relink compares the saved names inside the chosen folder and reports "N of M images missing".
- **Memory:** one decoded still at a time (`autoreleasepool` per frame); a 24-megapixel JPEG burst previews at 1080 px in ≈ 0.06 s per still on the owner's Mac.
- **Limitations:** no manual reordering; a still that decodes partially is not detected (ImageIO either decodes it or not); HEIF/HEIC depends on the Mac's ImageIO support and was not exercised on real HEIC files in this session (the loader accepts the type).

### D-023 · 2026-11-06 · Alignment: Vision registration to a reference, fixed analysis size, guarded, cached
- **What:** optional, off by default (PRD §6.1). Every selected frame is registered to a reference frame with Vision (`VNTranslationalImageRegistrationRequest`; "Perspective" mode adds `VNHomographicImageRegistrationRequest`) and moved onto it **before** the reducer sees it (`CompositeRenderer.aligned`). The reference is the middle selected frame by default (the documented automatic choice) or the frame under the playhead; a reference that is no longer selected falls back to the middle and the UI says so.
- **Analysis size:** registration runs on 8-bit sRGB renderings of the frames at a long edge of at most 2048 px (`RegistrationEngine.analysisLongEdge`), through the same Lanczos-in-linear-light path as everything else; transforms are scaled back to source pixels. This keeps Vision cheap (≈ 25 ms per 1920 px frame on the owner's Mac) and, more importantly, makes the transforms **independent of the output size** — a 1080 px preview and a full-resolution export use the same transforms (asserted by tests). Precision is about one analysis pixel: ≤ 1.9 px at 4K, 2.8 px on a 24-megapixel still. A "full-resolution precision" option can come later if stacking sharpness demands it.
- **Guards (never silently wrong):** a shift that would leave less than half the frame overlapping is rejected and the frame is **left out** of the composite and counted as *failed* (a misaligned frame would smear exactly what alignment is meant to fix; the count is in the summary and `framesComposited` tells the truth); in Perspective mode the homography is used only if every corner lands within max(4 px, 2 %) of where the plain shift puts it (and is plausible), otherwise the frame falls back to the shift and is counted as *fell back*. Both counts and the largest applied shift are in `AlignmentReport` and shown in the inspector. On the block-noise fixture Vision's homographies are wild (−5 px where −12 px is right), which is exactly what the guard is for.
- **Edges and coverage:** moved frames leave uncovered canvas; the frame is rendered transparent there (the Lanczos clamp is cropped back to the frame's own scaled extent), so the accumulated alpha records coverage, an Average is the mean of the frames that cover each pixel, and exports carry alpha (D-022). The intersection of all frames (`validArea`, the "safe area") is reported in output pixels and drawn as a yellow dashed rectangle on the preview (toggle in the Alignment section); M5c's crop-to-valid-area will use it.
- **Cache:** registration outcomes (transform + failed/fell-back flags) are cached per (source path + size stamp, reference, mode) inside the renderer, so an export after a preview recomputes nothing (`fromCache`) and reports the same failures; the main thread never runs Vision. Found while testing: a first version cached only the transforms, so a cached run reported "59 aligned" where the original had rejected 16.
- **Verified:** synthetic handheld fixtures (8 frames cut from one static scene at known integer offsets; PNG lossless and H.264 crf 12): every shift recovered within 0.5 px (PNG) / 1 px (video), the aligned Average equals the reference frame inside the safe area (mean |Δ| < 0.002 lossless), the unaligned one blurs. Real footage: the iPhone walking clip — 10 consecutive frames align with a 2.2 px max shift and a visibly sharp composite; over 60 frames of forward walking Vision returns shifts of hundreds of pixels for 16 frames (the scene flows, there is no global 2-D motion to find), the guard leaves those out and the remaining 43 align within 3.6 px — the honest answer for footage alignment cannot fix.
- **Limitations (PRD §6.1 "avoid claims of perfect alignment"):** global 2-D motion only; parallax, forward motion, rolling shutter and moving subjects are not modelled and may be mis-registered within the guard limits; Vision's translation result is **integer** at the analysis size (the probe on the iPhone clip shows shifts of exactly 1.0/2.0 px), so sub-pixel stacking precision is not available; no manual nudge; rotation/zoom only through the guarded Perspective mode. Alignment adds roughly one extra analysis render + Vision call per frame (≈ 5× the plain preview time on the 60-frame iPhone test: 1.63 s vs 0.32 s).

### D-024 · 2026-11-06 · Geometry after the composite: straighten, crop, edge fill; Fit/Fill canvas for stills
- **Post-composite, not per frame:** `GeometrySettings` (counter-clockwise straighten angle ±45°, a crop in canvas-normalised units, an edge fill) is applied once to the finished `LinearImage` by `GeometryProcessor` (Core Image rotate about the canvas centre with the canvas size kept, crop, then fill). The per-frame math is untouched, there is one resample instead of one per frame, and preview = export by construction because both go through the same function on the same composite. The crop is stored normalised so it survives any output size (a 50 % export crops to half the pixels).
- **Crop to safe area:** `largestValidCrop` computes the largest axis-aligned rectangle inside the alignment valid area (D-023) after the straighten angle (the classic largest-inscribed-rectangle closed form, centred on the rotated valid-area centre) — one click removes both the moved-frame edges and the straighten corners. Verified: a 10° straighten + "crop to safe area" leaves no transparent pixel.
- **Edge fill:** Transparent (default: PNG/TIFF keep alpha, JPEG flattens onto black and says so), Black or White (composited in linear light, alpha becomes 1 in every format). It is in the Crop & Straighten section because the three sources of empty pixels — aligned frames, letterboxed stills, straighten corners — all end up here.
- **Fit/Fill for mixed-size stills (PRD §4.2 canvas policy):** the strict default still refuses a folder of mixed sizes with the file names; the failure screen then offers **Fit** (uniform scale inside the first image's canvas, centred, transparent bars) and **Fill** (uniform scale to cover, centred, overflow cropped). The choice is per sequence (`CanvasPolicy`, saved in the project reference as `canvasPolicy`; absent = strict), switchable in the Source section, and the Source section says how many images were scaled. Nothing is ever stretched. A phone burst mixing landscape and portrait shots therefore works as a letterboxed Fit or a cropped Fill, by explicit choice.
- **Per-source settings:** alignment and geometry reset to their defaults when another video or folder is opened directly (a project restores its own); blend, sampling and export choices carry over like preferences, as before. Found in the window: a −1.6° straighten and "align" left on from the previous clip made a freshly opened folder show "1 frame, 4 could not be aligned".
- **Undo steps for drags (simplifies D-018's grouping):** interactive edits (slider and handle drags) no longer open nested undo groups inside the window's per-event group; `beginInteractiveEdit` remembers the settings, intermediate values register nothing, and `endInteractiveEdit` registers one named step from the start value to the end value. Same behaviour, no nesting, and it works identically with a manager that groups by event (the window) and one that does not (tests; `UndoNamingTests`, `UndoNamingEventGroupTests`). Lesson recorded for the GUI scripts: the accessibility `name` of SwiftUI's Edit › Undo item is the static "Undo"; the drawn title ("Undo Change Alignment", "Undo Straighten") is only visible on screen — a screenshot of the open menu is the check, not the AX name. An intermediate attempt that called `setActionName` outside any open group aborted the test process (`freed pointer was not the last allocation`); hence the test.
- **Not done:** crop handles on the preview (the fields and the two buttons are the M5c UI; direct manipulation is a polish item), aspect-ratio presets, perspective crop. The safe-area overlay is hidden while a straighten angle is set (a rotated valid area is no longer axis-aligned); "Crop to Safe Area" still accounts for the angle.

### D-025 · 2026-11-06 · Temporal weighting: timestamp-normalised curves, weighted Average, raw weights elsewhere
- **Model (PRD §5.3):** `WeightCurve` is Flat, Favor Early, Favor Late, Favor Middle or Custom (five draggable control points, linearly interpolated). It is evaluated at each selected frame's **normalised timestamp** t = (time − first)/(last − first), so variable-frame-rate footage and sparse Every-Nth selections are weighted by when a frame was recorded, not by its index. Presets never reach zero: `0.1 + 0.9 × shape(t)` ("favor", not "exclude"); a single selected frame sits at t = 0.
- **Per mode:** Average is the weighted mean `Σ w·frame ÷ Σ w` (weights normalised, so brightness is unchanged and Flat reproduces the plain Average bit for bit — asserted). Additive adds `w × frame` without normalising (exposure accumulation, as the PRD allows "intentionally"). Screen / Multiply / Difference / Normal multiply each frame's opacity by its raw weight; the first frame still initialises the composite. Lighten / Darken have no weights; the report says so instead of pretending.
- **Zero-weight guard:** a curve that is zero at every selected frame falls back to Flat and the report says so; a reducer whose total weight is zero throws rather than producing NaNs.
- **Report and UI:** the Weighting section draws the curve with one tick per selected frame at its real timestamp (sub-sampled above 400 frames) and states the raw range and the "effective frame count" `1/Σw²` (what the weighted average is statistically worth; N for Flat). `CompositeResult.weighting` carries the same for preview and export.
- **Undo and projects:** `CompositeSettings.weighting` (absent in older documents = Flat); custom-point drags coalesce into one "Change Weighting" step; a fresh source resets to Flat like alignment and geometry.
- **Not done:** curve smoothing (points are linear), more than five custom points, a weight read-out per frame on the filmstrip.

### D-026 · 2026-11-06 · Exact Median in bands; whole-pixel Max/Min Luminance
- **Median is exact, never approximated (PRD §5.2):** the per-channel median across the selected frames needs every frame's value at a pixel, so it cannot stream. `MedianPlan` splits the output into horizontal bands whose complete Float32 history fits a budget (1 GiB by default; `CompositeRenderer(memoryBudgetBytes:)`), and the renderer decodes the selection once per band through the normal per-frame pipeline (orientation, alignment, resampling restricted to the band rows) into a `MedianBandAccumulator`; each band's median (quickselect per sample, pixels in parallel; even counts take the mean of the two middle values; NaN sorts last) is assembled into the final image. Band seams are invisible by construction and a 26-pass render equals a 1-pass render bit for bit (asserted). Alignment registration is cached, so it runs once however many passes; weights are ignored and reported as such.
- **Cost, stated honestly:** passes = ⌈rows ÷ (budget ÷ (width × 16 B × N))⌉ — a 1080 px preview of 600 frames is 2 passes, a native 1080p export 19, a 4K export of 1,000 frames ≈ 90 (the clip is decoded that many times). The Blend section states the pass counts for the current preview and export before anything renders, the bottom bar shows "pass p of P" while it runs, and the result's `MedianReport` records what happened. Float32 history was chosen over Float16 for exactness and because `Float16` is unavailable on Intel Macs.
- **Max/Min Luminance:** at each pixel the complete RGBA of the single frame with the greatest/least linear luminance (0.2126 R + 0.7152 G + 0.0722 B on premultiplied values, Rec. 709 / sRGB primaries). Streaming, order-independent, ties keep the earlier frame, no opacity, no weights. Distinct from Lighten/Darken, whose per-channel extremes can produce colours no frame had (asserted on a red / gray / blue triple).
- **Verified:** moving-square median removes the trail entirely and keeps the static bar at the Average's value; count clip bit blocks at the 50/50 split come out at exactly 0.5; progress reports pass 1…3; an aligned median of the handheld stills equals the reference inside the safe area within 0.002.
- **Not done:** a user-facing memory-budget control; a faster approximate median (would have to be labelled as such); median of the alpha channel is taken per channel like colour.

### D-027 · 2026-11-06 · Motion mask: masked frames feed the blend, the composite is laid over the background
- **Method (PRD §6.3, "simple, transparent"):** the background is the exact Median of the selection (default) or one selected frame (the playhead's; a frame that is no longer selected falls back to the median), rendered at output size through the same pipeline (alignment included). For every frame the linear-light Euclidean RGB distance from the background is thresholded (default 0.08), opened-then-closed with a small radius (specks and pinholes, default 1 px), box-blurred three times (feather, default 2 px) and optionally inverted. Radii are in native canvas pixels and scale with the output size so preview and export mask alike.
- **One mechanism for every blend mode:** the frame is multiplied by its mask — it becomes a premultiplied RGBA frame whose alpha is the mask — and goes through the chosen reducer unchanged; the finished composite is then laid over the opaque background. Average therefore gives Σ(M·F)/N over the background (a ghost proportional to how often a subject was at a pixel, exactly like a long exposure of only the moving parts), Lighten/Max Luminance keep the brightest moving pixels, Median shows a pixel only if it moved in more than half the frames, and **Normal + mask is chronophotography** (each moving region laid over the earlier ones in time order). The Motion Mask section states the recipe for the current mode. Motion accumulation therefore needs no separate mode.
- **Found and fixed while testing:** the sequential modes (Screen, Multiply, Difference, Normal) assumed opaque frames — a masked-out pixel (alpha 0) wiped the composite to black under Normal. They now follow the W3C compositing rule for a partly covering source, `B' = (1 − a_F)·C + a_F·B(C, F ÷ a_F)`, which is the plain blend for opaque frames (all earlier fixed-value tests unchanged) and exact source-over for Normal. This also makes aligned frames' transparent edges behave under those modes.
- **Coverage view:** the per-pixel mean mask over the composited frames (0…1) is kept with the result and can be shown instead of the composite ("Show mask coverage"), cropped/straightened like it; the report gives the mean coverage and the fraction of the image that is background only.
- **Cost:** the background costs one extra render (a Median for the default — band-wise, see D-026), then per frame a distance map, 4 morphology passes and 6 blur passes over the output — scalar Swift loops, ≈ 10 ms per 1080 px frame on the owner's Mac; vDSP/vImage if that ever matters. (It mattered at full 4K: measured and made parallel in the M6 exit review, D-038.)
- **Limitations (stated in the UI):** anything that differs from the background counts as motion — moving shadows, lighting changes, camera motion (align first), noise above the threshold; no semantic understanding (PRD: "do not promise semantic recognition"); no per-region blend modes yet.

### D-028 · 2026-11-06 · Painted mask: vector strokes in the project, rasterised per output size
- **Storage (PRD §6.4 "vector strokes or a resolution-appropriate raster"):** strokes, not pixels. Each stroke is a polyline in canvas-normalised coordinates with a radius as a fraction of the canvas long edge, a softness and an erase flag, stored in `CompositeSettings.paintedMask`. They are tiny, resolution-independent, diff-able in the JSON project, and each stroke is naturally one undo step ("Paint Mask" / "Erase Mask"; "Clear Painted Mask"). The raster is built on demand for the current output size (`PaintedMaskRasterizer`: soft discs stamped every quarter radius along the polyline; paint takes the maximum, erase the minimum with the inverted brush, in stroke order; invert flips the result), so preview and export agree by construction.
- **Semantics:** the painted mask multiplies each frame's alpha exactly like the motion mask (and with it when both are on: `motion × painted`), and the composite is laid over the same background (the Median of the selection or the playhead frame chosen in Motion Mask). Everything outside the strokes shows the background. The mask lives on the **unrotated canvas**: painting maps through the crop offset and is refused while a straighten angle is set (the section says so).
- **UI:** a "Paint on the preview" toggle turns drags on the composite into strokes with the current brush (size as % of the canvas, softness, Paint/Erase); existing strokes and the stroke in progress are drawn as translucent red (erase: blue) lines over the image.
- **Not done:** a resolution-appropriate raster export of the mask, pressure, smoothing of the polyline, painting on the Original view, per-region blend modes.

### D-029 · 2026-11-06 · Post-composite colour on a cached composite
- **Pipeline order (PRD §7 "identify before- vs after-composite adjustments and define stacking order"):** frames → (alignment, masks, weights) → reducer → **colour** → straighten/crop/edge fill → encode. Colour is applied to the finished linear composite, never per frame, so the mathematics of every blend mode is untouched and the edge-fill colour stays what the user chose.
- **Maths (documented, tested):** exposure multiplies linear light by 2^EV; white balance applies per-channel linear gains from two sliders (temperature ±30 % on red/blue in opposite directions, tint ∓20 % on green — a deliberately simple, documented model, not a correlated-colour-temperature model); saturation lerps from the Rec. 709 luminance in linear light (−1 = gray, +1 = double chroma); contrast works in sRGB-encoded values around mid-gray 0.5 (`0.5 + (e − 0.5) × (1 + c)`, clamped) because that is what "contrast" means perceptually, and returns to linear. Pixels with partial alpha are adjusted as straight colour. No curves yet (PRD lists them as optional).
- **Cache (PRD §10.1):** the model keeps the last `CompositeResult` keyed by (source, compositing settings, preview quality); when only colour or geometry changed, the preview re-runs the post pipeline on that image without decoding a frame (`previewRenderCount` proves it in the tests: exposure and crop changes do not render, a blend change does). Geometry edits therefore became instant as well — until M6e every straighten/crop step re-decoded the clip. One composite is cached (the latest); exports always render at their own size.
- **Verified:** exports at +1 EV are exactly twice as bright in linear light as at 0 EV through the whole file path; identity is a no-op.

### D-030 · 2026-11-09 · Presets carry choices, not places; batches render each distinct composite once
- **Preset contents (PRD §9.2 "without hardcoding source file identity or an absolute timeline"):** sampling kind/N/count, blend and opacity, alignment on/off and mode, weighting curve, motion-mask parameters, the painted mask's invert switch, straighten angle and edge fill, colour, and the export settings (format, depth, JPEG quality, sizing, colour space). **Never** the time range, the crop, painted strokes, a frame-indexed alignment reference or mask background (those become "middle"/"median"), or anything naming the file. Applying a preset therefore keeps the open document's range, crop and strokes and says so; sampling the range cannot honour ("Exact Count 300 … all 24 are used") is reported, and the sampler clamps as it always did.
- **Storage:** one JSON file per preset (`SettingsPreset`, `formatVersion` 1, sorted keys, ISO dates) in `~/Library/Application Support/FrameStack/Presets/<name>.framestackpreset`; the folder is the truth (re-read on demand, so files copied in appear; unreadable or newer-format files are listed as problems, not fatal). Saving refuses to overwrite a different preset of the same name unless the user confirms. Alternatives: presets inside the project file (not reusable across clips), UserDefaults (opaque, not shareable). Revisit if presets need ordering, folders or built-in starters.
- **Apply = one undo step** ("Apply Preset"), implemented by suppressing the per-field steps while the fields are set and registering the start→end difference, like a slider drag (D-018).
- **Batch (PRD §9.3):** the sheet offers the current settings, any other blend modes laid over them, and saved presets (each with its own export settings and sampling); identical outputs are merged. File names follow the single export (`<base> <variant> <N>f[ <long edge>px].<ext>`) and are made unique against the folder and each other with " 2", " 3", … before the extension, case-insensitively — deterministic for the same inputs and folder contents. `BatchExporter` groups variants by (compositing part, output size), renders each group once and writes every member from that composite (colour and geometry per variant), one group at a time, so memory is bounded by one output-sized composite; every write is atomic and read back. Cancelling stops after the current frame; unwritten outputs are marked cancelled and nothing partial is left. Single export and preview rendering pause while a batch runs.
- **Verified:** 5 variants over the moving-square clip → 3 render passes, a pre-existing file untouched and the new one suffixed " 2", +1 EV variant exactly 2× the Average in linear light through the file, half-crop and 240 px variants sized as asked; cancellation after the first of three 150-frame outputs leaves exactly one file; a variant that cannot be sampled fails alone while a Median variant beside it renders in bands.
- **Not done:** built-in starter presets, preset import/export UI beyond "Show in Finder", per-variant file-name templates, a batch over several clips (one source per batch, as the PRD states), running a batch while editing continues.

### D-031 · 2026-11-09 · Tone curve: a monotone-cubic master curve on encoded values, last in the colour chain
- **Decision (PRD §7 "optional curves"):** `ColorAdjustments.curve` is one master curve applied to R, G and B alike, on sRGB-encoded values 0…1, after contrast (order: exposure → white balance → saturation → contrast → curve → straighten/crop). Five control points at fixed inputs (0, 25, 50, 75, 100 %) are dragged vertically in the Color section; a Shape menu offers Linear, Soft Contrast, Strong Contrast, Lift Shadows, Fade and Matte. The points live in the project and in presets; older files without a curve decode to the identity.
- **Interpolation:** a monotone cubic Hermite spline (Fritsch–Carlson tangents): it passes through every point, never rings above or below two neighbouring points, and is monotone when the points are — a natural cubic or Catmull-Rom spline would overshoot and could invert tones. Evaluated per image through a 4,096-interval lookup table (encoded in → linear out, linear interpolation); the table agrees with the spline to < 2 × 10⁻⁶ in linear light, far below one 16-bit step.
- **Identity is skipped entirely**, so values above 1 (Additive overflow) survive as before; once a curve is active the input is clamped to 0…1 first, as contrast already does.
- **Alternatives:** per-channel R/G/B curves and free point insertion/removal (more UI than a single creative user needs now; the stored format is already a list of arbitrary points, so both can be added without a format change); a curve in linear light (not what photographers mean by a tone curve).
- **Verified:** the curve passes through its points, stays between neighbours, is monotone for monotone points; a lifted mid-point maps encoded 0.5 to exactly the linear value of encoded 0.75; an 8-bit export with Lift Shadows equals the curve applied to the plain export's values within rounding; a curve change re-processes the cached composite without decoding (render count unchanged); undo name "Change Tone Curve"; project and preset round trips.
- **Revisit trigger:** a need for per-channel colour grading or more than five points.

### D-032 · 2026-11-09 · Frame selection: take/skip pattern, per-frame overrides, reverse stacking for any source
- **Decision (PRD §4.3, §5 order-dependent modes):** three additions to "which frames, in which order".
  1. **Pattern sampling** — `SamplingMode.pattern(take:skip:)`: starting with the first frame of the range, take `take` frames in a row, skip `skip`, repeat. `take ≥ 1`, `skip ≥ 0`; `take 1 / skip n−1` is exactly Every Nth, and the pattern always starts at the range start, so moving the range moves the pattern with it.
  2. **Frame overrides** — `FrameOverrides` holds two disjoint, sorted sets of exact timestamps: *excluded* and *always included*. They are applied **after** sampling: an excluded frame is removed and nothing takes its place; an included frame is added in time order whatever the sampling says. An override outside the time range (or naming a timestamp the timeline does not have) stays stored and does nothing, and is counted as inactive. Excluding every selected frame is an error (`allFramesExcluded`), never a silently different composite.
  3. **Reverse stacking order** — `CompositeSettings.reverseOrder` stacks the selected frames last to first. It only exists for the order-dependent modes (Screen, Multiply, Difference, Normal); for every other mode `compositingPart` normalises it to false, so toggling it there reuses the cached composite and batch variants share a render. Weights stay with each frame's timestamp: reversing does not flip a Favor Late curve.
- **Reverse decode of video within a budget:** a video can only be decoded forwards. The renderer cuts the selected span into chunks that fit `CompositeRenderer.memoryBudgetBytes` (1 GiB by default) of prepared frames, decodes each chunk forwards starting from the last chunk, holds that chunk and feeds it to the reducer backwards. Cost: one reader restart per chunk; memory: one chunk. The preview reports "Stacked last to first in N chunks of up to M frames". Image sequences simply iterate backwards.
- **Where they live:** pattern and reverse are creative choices (projects, presets, carried over to the next source). Overrides name frames of one source: they are in the project, are **not** in presets (applying a preset keeps the document's and says so), do not affect "matches preset", and are cleared when another source opens. No project format bump: all three fields decode as "absent = off".
- **UI:** Sampling gains a fourth segment, Pattern, with Take and Skip steppers. Under it, "Frame under the playhead" is a three-way Auto / Include / Exclude control with a plain-language status and a Clear Overrides button; **X** on the focused timeline toggles Exclude. The timeline draws a red cross on excluded frames and a white dot on always-included ones (dimmed outside the range). The bottom bar reads "150 frames in range → 59 selected (1 excluded, 1 added)". Blend shows **Reverse stacking order** only for order-dependent modes. Undo names: Change Sampling, Exclude Frame, Always Include Frame, Clear Frame Override(s), Reverse Stacking Order.
- **Relation to the sequence toggle (D-022):** a folder of stills keeps its own Reverse order, which reverses the *source timeline* (range, weights and thumbnails follow). Reverse stacking order leaves the timeline alone and changes only which frame ends on top. Using both cancels out for the stacking and is allowed.
- **Alternatives:** overrides as frame indices (break when a file is relinked to a re-encode with the same timestamps but a different count; timestamps are the identity everywhere else — D-006); excluded frames replaced by the nearest neighbour (fabricates a selection the user did not ask for); holding every frame for a reverse pass (unbounded memory) or seeking per frame (very slow on long-GOP footage); reversing weights with the order (two meanings behind one switch).
- **Verified:** core `FrameOverridesTests` ×13 and a preset test; media `ReverseOrderRenderTests` ×9 (Normal reversed shows the first frame; reversed equals a by-hand reverse reduction for Normal, Difference, Screen and Multiply to < 1e-5; a budget of 7 frames gives 5 chunks and a bit-identical image with monotonic progress; order-independent modes ignore the switch; weights stay with timestamps; cancellation; sequences; batch variants); app `FrameSelectionAppTests` ×4 (undo names, summary text, cache reuse, exported top frame 0 / 2 / 1 / 148 / 149, project and preset round trips, a new source drops only the overrides).
- **Known limit found while testing:** on the damaged fixture a forward pass loses frames 73…89 around the corrupt sample 75, while a reader that *ends* before the damage still returns 73 and 74 intact, so a chunked reverse pass can keep a frame the forward pass loses. Both report their missing frames truthfully (D-013); the two orders can therefore differ by a frame or two on a damaged file. Recovering those frames in the forward pass (restart the reader to end just before the damage) is possible and not done.
- **Revisit trigger:** range selection of overrides (exclude a whole stretch at once), manual drag reordering (PRD optional), or damaged real footage where the forward/reverse difference matters.


### D-033 · 2026-11-09 · Range segmentation is a batch option; starters are built-in looks that leave corrections alone
- **Decision (segments, PRD §4.3 / §5.3 "temporal range segmentation"):** the batch sheet gains **Split the range**: every chosen version (current settings, other blend modes, starters, saved presets) is exported once per part, optionally with the whole range as well. `RangeSegmenter.segments(of:in:count:)` divides the **eligible frames** of the range into N consecutive parts by frame count: `total ÷ N` each, the first `total mod N` parts get one more. Boundaries are frame timestamps; the first part starts at the range start and the last ends at the range end, so the parts are half-open, disjoint and together equal the range exactly (`[start,end)` preserved). N is clamped to the frame count and to 99.
- **What a part is:** an ordinary variant whose settings differ only in `rangeStart`/`rangeEnd`. Sampling, the take/skip pattern, weighting (curve position is relative to the part), motion-mask background and alignment reference are therefore evaluated **inside each part**: Every 10th restarts at each part's first frame; an Exact Count larger than a part uses the whole part. A `.frame(t)` alignment reference or mask background outside a part falls back to the automatic choice, as it already does for any selection that does not contain it. Frame overrides are timestamps and keep working where they fall.
- **Names:** `"<base> <version> part 03 of 12 <count>f.<ext>"`, zero-padded so Finder sorts them in time order; each file carries its own frame count (parts of 34, 33, 33 are named 34f, 33f, 33f). Collision handling is the batch's (D-030).
- **Cost:** parts never share a composite (different frames), so the pass count is versions × parts, shown before starting. Each pass decodes only its part, so the total decode work is about one pass over the range per version. Memory stays one output-sized composite. The progress list scrolls past 12 outputs so the sheet stays on screen.
- **Decision (starters):** six built-in looks — Long Exposure, Light Trails, Dark Trails, Empty Scene, Action Sequence, Fading Echo — defined in code (`StarterPreset.all`), listed above the saved presets in the Presets menu and tickable in the batch sheet. A starter sets only the sampling choice (and the one parameter it uses), blend mode, opacity, stacking order, weighting and the motion mask's on/off (with Median background, not inverted). It **keeps** alignment, straighten/crop, colour and tone curve, the painted mask, frame overrides, the time range, the motion mask's threshold/feather/clean-up and the **export settings**. Applying one is a single "Apply Preset" undo step with the same kept-from-document notice style as saved presets.
- **Why starters differ from saved presets (D-030):** a saved preset is "this exact look, everywhere", so it replaces colour, geometry rotation and export settings. A starter is "show me this kind of picture from what I have", tried repeatedly on a document that may already be aligned, cropped and graded; resetting those would punish experimenting. A new document equals Long Exposure, so the menu button names it from the start.
- **Alternatives:** splitting by equal seconds (variable-frame-rate clips and folders of stills would give uneven or empty parts; counts are what the file name states); a separate "Segments" export command (duplicates the batch's naming, progress, cancellation and reuse); starters as `.framestackpreset` files written into Application Support on first launch (they could be deleted or edited into something the README no longer describes, and would overwrite export settings); sliding/overlapping windows (a different feature — every frame would be decoded many times; not requested).

### D-034 · 2026-11-09 · The crop is edited on the preview over the whole canvas; shape lock is tool state
- **Decision (PRD §6.2 crop handles, aspect presets):** **Edit Crop on Preview** (inspector button, View ▸ Crop on Preview ⌘K, a Done button on the preview) switches the preview to the **whole straightened canvas** with the crop drawn over it: dimmed outside, thirds grid, corner and edge handles. Only the display changes: `displayGeometry` is the document's geometry with the crop set to full; exports and batches always use the real geometry, and leaving the mode shows the cropped picture again. In Fit zoom the canvas is inset by 44 pt while editing so the handles on the canvas edge clear the window edge and the Done bar.
- **A drag is one edit:** while the pointer moves only a draft rectangle changes (`cropDraft`, canvas pixels); the release commits it as one undo step named "Change Crop". A crop-only change while editing does not process the picture again (the cached post-processed image is re-stamped; the same image instance stays on screen). A press that goes nowhere is not an edit and adds no undo step.
- **What a drag does:** a corner or edge moves that side; inside the crop moves it; a drag that starts outside the crop, or anywhere when the crop is the whole canvas, draws a new one. Handle drags stop at 16 px a side (or the canvas side if smaller); the number fields still go to 1 px. Results are whole canvas pixels, clamped to the canvas.
- **Shape lock:** Free (default), Original (the canvas's own shape) and 1:1, 5:4, 4:3, 3:2, 16:9, 2:1, with **Flip Shape** for portrait. Choosing a shape reshapes the crop about its centre keeping its area where the canvas allows (one undo step). With a lock: a corner follows the pointer on the axis that has gone furthest, so the crop always reaches the pointer; an edge drag grows the other dimension about the crop's centre line; a number field makes the other side follow, or gives the largest rectangle of the shape that fits from that corner; **Crop to Safe Area** gives the largest rectangle of the shape inside the safe area. The lock is **tool state**: it is not saved in the project or in presets, and a new source or Reset returns it to Free. The read-outs name the shape when the crop matches a preset ("1920×1080 · 16 : 9").
- **Mode rules:** painting a mask and editing the crop are mutually exclusive (both use drags on the preview); switching to the Original view ends crop editing and starting it from the Original view switches to Composite (Side by Side keeps it); a new source ends it.
- **Alternatives:** dragging handles on the already-cropped preview (the area outside the crop is not visible, so a crop could only shrink); a separate crop window or sheet (a second place showing the picture, away from the straighten slider that changes the canvas); committing every pointer move (one undo step per pixel and a post-process per move); saving the lock in the document (a locked shape would then silently constrain a crop typed months later; the crop itself already records the result); free-form ratio entry (the presets and Original cover the PRD's list; a custom ratio is two number fields away).
- **Verified:** core `CropEditingTests` ×12 (every handle, limits, locked drags, drawing, fitting, inscribing, names); app `CropAppTests` ×5 (whole canvas while editing with export and cropped preview unchanged and pixel-equal, one undo step per drag with no extra render, shape lock through drags, fields, flip and safe area, what ends the mode, handle hit-testing). GUI: mode on and off, overlay, margin, read-outs and Crop to Safe Area seen on a background instance; a pointer drag on a handle was **not** driven (see the plan's log).
- **Revisit trigger:** a request for a custom ratio, for the lock to persist, for rotating by dragging outside the crop, or for arrow-key nudging of the crop.

### D-035 · 2026-11-09 · Camera RAW stills: Apple's default rendering, developed at the size the output needs
- **Decision:** a folder (or selection) of camera RAW files is an image sequence like any other. Each file is developed by Core Image's RAW decoder (`CIRAWFilter`) with **Apple's default rendering** (as-shot white balance, default tone, noise reduction and lens handling as macOS chooses) and enters the pipeline as a display-referred picture converted to linear light, exactly like a JPEG of the same shot. There are **no RAW development controls** (exposure, white balance, highlight recovery before stacking); the post-composite colour controls (D-029) work on the result. Which cameras decode is whatever this macOS supports: a file the decoder refuses is skipped and listed like any unreadable still, and FrameStack makes no promise about a particular camera.
- **Orientation once:** the decoder is told to leave the picture as stored (`orientation = .up`) and the header orientation is applied in the common still path, so a rotated RAW is turned exactly once (`testOrientationTagRotatesTheRAWOnce`).
- **Reduced decode, one resample:** when the output is at most half the stored size, the decoder is asked for a 1/2, 1/4 or 1/8 picture (the largest reduction that still covers the output) and that picture goes **straight to the output scale**; it is not first enlarged to the stored size. A decoder result whose size differs from the header size is treated as covering the whole stored frame. Only with alignment on is it brought to the canvas first, because the aligner works in canvas pixels. Full-size output always uses the full decode.
- **Measured (8 Sony ILCE-7RM5 ARW, 9504×6336, read in place on the owner's Mac):** headers of 8 files 0.13 s; filmstrip (embedded previews) 0.14 s; 1600 px Average of 8 **4.05 s, 506 ms a frame, footprint +1.6 GB**, colour within 0.0003 of ImageIO's rendering of the same file; full-size Average of 2 frames 3.59 s with a **peak footprint of +6.1 GB**. Enlarging the reduced decode first (the first implementation) cost 667 ms a frame and +2.8 GB.
- **Known limits:** (1) full-size RAW stacking of 60-megapixel files needs about 6 GB while a frame is developed (Core Image float intermediates); it fits this 24 GB Mac but is the heaviest thing the app does, and the memory-pressure handling in D-036 is the backstop. (2) A shot present twice, as RAW and as JPEG/HEIC of the same name, counts twice; the source notice says so and how many (`rawPairCount`), it does not drop either. (3) ~~Opening a folder whose files are iCloud placeholders makes macOS download each one as its header is read~~: fixed the same day, placeholders are left out unopened and listed (D-037). (4) The filmstrip shows each RAW's embedded camera preview, which can differ slightly in colour from the developed frame; the Original view and the composite use the developed picture.
- **Alternatives:** scene-linear RAW (decoder output before the tone curve), rejected: it would make RAW stacks look unlike the camera's own JPEGs and unlike every other viewer, and needs the development controls this app does not have. ImageIO's RAW path, measured equal in colour (within 0.001) but with no reduced decode, so previews paid for the full 60 megapixels. Always decoding full size: about 1.8 s a frame for a preview.
- **Verified:** `RawStillTests` ×8 on synthetic 16-bit linear DNGs (import as RAW, an unreadable RAW skipped and listed, the default rendering is neutral, monotonic and keeps hues, Average equals the mean of the developed frames, orientation, reduced decode keeps geometry and colour, RAW+JPEG pairs reported, reduced decode with alignment and with mixed sizes) plus the opt-in `testOwnerRAWFolder` on the owner's ARW files (figures above; it skips iCloud placeholders without opening them); app `testFolderOfRAWFilesOpensToAPreviewWithTheRAWNotice`.
- **Revisit trigger:** the owner wants exposure or white balance per RAW before stacking, a camera macOS cannot read, or full-size 60 MP stacks on a Mac with less memory (tiling the develop step).

### D-036 · 2026-11-09 · Memory pressure stops the heavy work with a message; log-tagged clips are warned about, untagged ones are not
- **Memory pressure:** the app listens to the system's memory-pressure source. **Warning:** Core Image's pooled memory is released (`CIContext.clearCaches`); nothing visible changes and running work continues. **Critical:** the kept composite (the one that makes colour and crop edits instant) is dropped and whatever is running is cancelled: a preview render shows "Stopped because macOS reported that memory is critically low. Close other apps, or choose a smaller preview quality or export size, then try again." with the usual Retry; an export ends as failed with the same text and writes nothing; a batch cancels its remaining outputs and the sheet keeps the reason. **Nothing restarts on its own** (the preview refresh that normally follows an export or batch is skipped once), because restarting is what would take the memory again. The picture already on screen stays.
- **Why not more:** per-frame memory checks or an own budget for Core Image were rejected as guesswork; the measured bounds (history budget D-026, banded median, reduced decodes) are the design, and this is the backstop for the cases they do not cover (60 MP RAW at full size, other apps).
- **Not simulated:** real system-wide pressure (`memory_pressure -S`) needs root and would squeeze the owner's whole Mac, so the tests call the handler the system event calls. What `clearCaches` gives back was not measured.
- **Transfer tags:** a clip whose transfer-function tag says **logarithmic** (H.273 values 9 and 10, which AVFoundation reports as `TransferFunction#9`/`#10`, or any tag naming "log") gets a source notice that there is no log conversion and the frames are stacked as stored. A tag FrameStack does not know gets a notice naming it. **Untagged clips get no notice:** they are common (screen recordings, older cameras, the two new regression clips), they are read as Rec. 709 (D-005), and a notice on each would train the owner to ignore notices. Consequence, stated plainly: camera log footage that is untagged or tagged Rec. 709 (the usual case for S-Log, C-Log, V-Log files) **cannot be detected** and is stacked as if it were ordinary video. HDR (PQ/HLG) keeps its existing notice (D-020).
- **Verified:** app `RawAndMemoryAppTests` ×5 for pressure (warning changes nothing and keeps the cached composite; critical while idle drops only the cache; critical stops a pending and a running preview until Retry; critical stops an export with the message, no file, no hidden re-render, and a later cancel is still a cancel; critical stops a batch, keeps the reason, leaves no partial files, and the next batch runs clean); media `RegressionClipTests` ×3 for tags (`log_tagged_8f.mp4`, tagged and untagged clips without a notice, the classification table).
- **Revisit trigger:** a real log clip the owner wants converted (add the camera's curve), or a pressure event seen in real use that this did not handle.

### D-037 · 2026-11-09 · Stills and project sources that are iCloud placeholders are never opened (closes the gap left by D-016 and D-035)
- **Problem found:** D-016 refused a *video* that is an iCloud placeholder, but a folder of stills was listed by reading every file's header, and reopening a project fingerprinted the saved source. Either read makes macOS download the file. This is what happened during the first RAW probes of M6k: up to about 10 of the owner's RAW files (at most about 680 MB) were downloaded by header reads. Nothing was modified or copied.
- **Decision:** one question, `CloudFiles.isNotDownloaded(url)`, asked **before any byte of a source file is read**: the `SF_DATALESS` flag from `lstat` (no read, no download), or the URL's ubiquitous-item status `notDownloaded`. It is asked in three places. (1) **Video import** (as before, D-016): refused with the "download it in Finder first" message. (2) **A folder or selection of stills:** each placeholder is **left out unopened** and listed (`ImageSequenceInfo.notDownloadedFileNames`); the source notice says how many images are in iCloud and names the first few; the frames that are on this Mac still open and stack. A folder with *only* placeholders fails with `MediaError.imagesNotDownloaded` and the same advice. (3) **Opening a project / relinking:** a placeholder still is counted as "N of M images stored in iCloud, not downloaded to this Mac" (separately from "missing"), and a single source file that is a placeholder is reported as changed with that reason instead of being fingerprinted. In both cases the relink sheet appears, so the owner can download the files and open the project again.
- **Why leave out rather than download:** downloading is a network action with a storage cost the owner did not ask for (the RAW folder is about 5 GB), and AGENTS.md rules out cloud services. Leaving the files out and saying so is the reversible choice; Finder's Download Now is one click.
- **Why not refuse the whole folder:** a shoot that is partly local is still useful to look at, and the notice states exactly what is missing. The project then records the files that were opened; reopening it later with more files downloaded keeps the saved list (D-022).
- **Verified:** `CloudPlaceholderTests` ×6. The file-system flag cannot be set by hand, so five tests answer the placeholder question themselves: placeholders are left out, listed and **never opened** (a placeholder with garbage contents would have been listed as unreadable had it been read), every image is asked about before it is read, a folder of only placeholders fails with the iCloud message, files on this disk are not placeholders, the project check reports "in iCloud" apart from "missing", and a placeholder source file is not fingerprinted. The sixth is opt-in on real placeholders (`FRAMESTACK_REAL_RAW_FOLDER=… swift test --filter CloudPlaceholderTests/testOwnerFolderPlaceholdersAreLeftAlone`): on the owner's folder of 87 Sony ARW files, **30 opened, 57 left out, 0.29 s, 57 placeholders before and 57 after** (counted from the flag by `ls -lO` as well).
- **Known limits:** a file that macOS evicts *while* a render is running is read (and downloaded) by the decoder, as with any app. The thumbnails and the Original view only ever touch files that were opened. Video placeholders are still refused, not offered for download.
- **Revisit trigger:** the owner wants a "Download and open" button, or works mainly from iCloud Drive.

### D-038 · 2026-11-10 · M6 exit review: measured performance, a faster motion mask, inspector order and wording, optional PRD items recorded as not done

"fps" is frames decoded per second of wall time; "peak" is the process high-water mark up to that row, so it only ever grows down the table.

  | Case | 1080 px preview, 1200 frames | Full 3840×2160, 300 frames |
  |---|---|---|
  | Average | 10.9 s · 110 fps | 5.2 s · 58 fps |
  | Lighten | 10.7 s · 112 fps | 3.0 s · 101 fps |
  | Average, Late weighting | 10.8 s · 111 fps | 5.9 s · 51 fps |
  | Max Luminance | 10.6 s · 113 fps | 5.4 s · 55 fps |

  | Normal + motion mask over a median background | 58.8 s · 20 fps | 53.9 s · 6 fps |
  | Lighten + painted mask (median background) | 55.6 s · 22 fps | 45.3 s · 7 fps |
  | Normal, reverse stacking order | 15.9 s · 75 fps · 12 chunks | 16.8 s · 18 fps · 38 chunks |
  | Average + alignment (shift) | 35.3 s · 34 fps · 1060 of 1200 stacked | 11.4 s · 26 fps · 262 of 300 stacked |

  Process peak over the whole run **4.31 GB**; the streaming modes stay under 0.5 GB at preview size. The clip is ffmpeg's moving test pattern, so the alignment row is a cost figure only: the registration guard (D-023) rejected 140 of 1200 frames (38 of 300) whose "shift" would have left less than half the frame overlapping, and they were left out and counted, as designed.
- **Reading it:** decode dominates the streaming modes (about 9 ms a 4K frame). Median is the expensive mode by design (one decode pass per band, D-026). Anything that needs a median background (the motion mask's default, and a painted mask without a chosen background frame) pays for that median first: about 45 s of the 55 to 59 s in the mask rows. Choosing a single frame as the background removes that cost.
- **Motion mask made parallel.** The first run of this table measured the motion mask at full 4K at **167.4 s for 300 frames, about 0.42 s a frame after the median**, against 18 ms at preview size: the clean-up and feather radii scale with the output, and the code was bounds-checked scalar loops over whole arrays, column by column for the vertical passes. `MaskOps` now works on raw buffers, runs rows (or columns) in parallel chunks on all cores, does the morphology as whole-row vector max/min (vDSP), and sweeps the vertical blur in memory order. Measured after: **53.9 s (about 47 ms a frame after the median, 9 times faster)**; preview size 66.8 s → 58.8 s (18 → 11 ms a frame). **The numbers are unchanged:** every value is produced by the same arithmetic in the same order as the serial loop. `MaskOpsReferenceTests` ×4 keep the old serial code as a reference and compare morphology exactly and the feather **bit for bit** on shapes from 1×1 to 900×400 with radii up to wider than the image, plus difference/threshold/apply and the chunking itself; the existing mask tests pass untouched.
- **Probe corrected, and a wrong sentence in the app.** The probe's check `composited + missing == selected` failed on the alignment rows. The renderer was right (rejected frames are neither composited nor "missing"; they are in `AlignmentReport.failedFrames`, and the inspector shows the count in orange). The probe now adds them and prints "N of M frames". The Alignment help text, however, said a frame that fails is "used unmoved": that contradicted D-023 and the behaviour. It now says the frame is left out of the composite and counted.
- **Inspector order: kept.** Project, Presets, Source, Time Range, Sampling, Blend, Weighting, Alignment, Motion Mask, Painted Mask, Crop & Straighten, Color, Export. It follows the work: what the document is, which frames (source, range, sampling), how they combine (blend, weighting), corrections applied while combining (alignment, masks), finishing the picture (crop, colour), output. Reordering by frequency of use was considered and rejected: sections collapse and remember their state (D-018), so the owner already controls what is in view, and a stable order is worth more than a slightly shorter scroll.
- **Wording tidied** (no behaviour change): the welcome screen and toolbar no longer speak only of video ("Open…", "a video, a folder of images or a project"; the format line names camera RAW); the relink sheet says "Source not found / Source has changed" since the source can be a folder; the project and save-panel texts say "source"; a clamped saved range names the right kind of source; "PRD §6.1" removed from user-facing help; "colour", "centre", "normalised", "initialises" and "cancelled" in help and status texts made "color", "center", "normalized", "initializes" and "canceled" to match the Color section and macOS. No test compares these strings.
- **PRD items marked optional or "later", recorded here as not done** (none is P0–P2 required work; none was dropped silently): manual drag reordering of stills (§ sources; natural filename order and Reverse exist); an encoded/gamma-space creative blend mode (all maths is linear light, D-005/D-017); configurable normalisation for Additive (post-composite Exposure exists, D-029); content-aware edge fill (transparent or solid fill and crop-to-safe-area exist, D-024); different blend modes for foreground and background or per region; per-frame or per-region masks (P3); per-frame preprocessing before the composite; a two-mode compare view (Original/Composite/Side by Side exists); auto-save; semantic segmentation (out of scope in the PRD).
